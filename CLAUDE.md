# CLAUDE.md

Project instructions for GMRLog. Read automatically at the start of every session — the rules below apply to all work in this repo without being restated.

## What this project is

GMRLog is a gaming identity product, not a game tracker. A player's profile answers one question: _what kind of gamer are you?_ Everything — the DNA match, archetypes, the platinum case, rarity — serves that. Features that only add numbers to a dashboard do not belong.

## Design law

**Tokens only.** Every colour, space, radius and type value resolves through `useTheme()` from `@gmrlog/ui`. A raw hex, a hardcoded pixel font size, or a literal `rgba()` in feature code is a bug. If a value has no token, the token is missing — raise it, do not inline it.

**The accent is a line, never a flood.** `color.accent.*` appears as borders, rings, glows, rules and text. It never fills a block behind content. The one exception is a primary CTA, and even there an outlined treatment is preferred. Test: switch to the `neutral` accent — if a screen stops making sense in monochrome, the accent was carrying meaning it should not.

**Rarity is geometry, not colour.** Legendary is a square plate with an ambient glow; common is a circle with a hairline. The colour ramp only brightens. This is why the system survives monochrome.

**Anything drawn on a scrim takes `color.scrim.foreground`.** A scrim is dark in _both_ schemes — that is the whole point of it, and `color.scrim.foreground` (`#F3F5FE`) is the one token deliberately identical in light and dark. Every `color.text.*` flips with the scheme, so a glyph over a scrim that takes `text.primary` renders near-black on near-black in light, and `text.inverse` does the same in dark. It is invisible, and no test catches it: typecheck, lint and unit tests were all green over the one instance that shipped (§14's glass buttons, found only by looking at the screen in light). The pair is `color.scrim.strong` for the plate and `color.scrim.foreground` for what sits on it — the pattern `HeroBackButton` establishes. **Measuring dark-first is what produces this**, so check a scrim in light before calling it done. Geometry alone is not the test: an opaque surface between the glyph and the scrim (an avatar, §13's emblem ring) breaks the relationship, and those glyphs correctly keep their normal tokens.

**Hairlines are whispers.** `color.border.default` is barely visible on purpose. Structure comes from space, not from drawn lines. If a layout feels loose after the palette change, add space or change surface — never darken the border.

**Weight 300–500 only.** Hierarchy comes from size, colour and space. Large numbers are light; nothing is bold to shout.

**Metadata is monospace.** Counts, timestamps, ranks, platforms, section kickers, the match token — all `role="meta"`, uppercase, tracked out. Sentences stay in `body`; names stay in `label` or `title`.

**One codebase, two platforms.** `apps/frontend` renders native and web from the same source through React Native Web. Never fork a web-only implementation. Tap targets ≥44px on both.

## Engineering rules

- **Compose from `@gmrlog/ui`.** Check the package before writing any new component. `Rail`, `StatTile`, `RarityBadge`, `DistributionBars`, `SegmentedTabs`, `Chip`, `Card`, `Avatar`, `EmptyState`, `Skeleton`, `ListItem`, `NavHeader` cover most needs. A new primitive needs a reason you can state.
- **Never delete a state.** Loading, empty, error and offline states already exist on every screen. Restyle them; do not drop them in a recomposition.
- **Scores are server-side.** The client never computes a match percentage, a rank or a points total. Two devices must never disagree.
- **Types flow through `packages/types`,** validation through `packages/validators`, API access through `packages/api-sdk`. No ad-hoc fetch in a feature folder.
- **Additive DTO changes.** New response fields are optional so existing consumers keep working.
- **One screen, one commit.** Even when several screens share a session.

## Known platform traps

React Native Web silently drops things rather than failing. Each of these was found by measuring a live screen, then rediscovered on a later one — they are written here so the third screen does not pay for them again. **None of them is a reason to fork a web-only implementation:** keep the correct cross-platform prop, which native reads, and record what the web build does with it.

- **`accessibilityValue` does not reach the DOM on a `View`.** A `progressbar` renders its `role` and `aria-label` but no `aria-valuenow`. Measured on the auth step rail (3.11). **Real fix, found by 8.2: add `aria-valuenow`/`aria-valuemin`/`aria-valuemax` alongside it.** These are not a web-only prop — see the standing rule below.
- **`accessibilityState` does not reach the DOM on a `Pressable`.** The element renders `role="button"`, `aria-label` and `tabindex="0"`, but no `aria-selected` / `aria-checked`. Measured on the same rail once its bars became tappable (3.12). **Real fix: add `aria-selected`/`aria-checked` alongside it** — same rule.
- **`accessibilityElementsHidden`/`importantForAccessibility`/`accessible={false}` — the "hide this decoration from assistive tech" trio — do not reach the DOM on web either, on either `View` or `Text`.** Found by 8.2, not suspected: the DNA match ring's wrapper `<div>` and a `Text` carrying the same three props both rendered with no `aria-hidden` attribute at all, meaning nothing marked decorative anywhere in the app (`EmptyState` medallions, `Icon`'s `decorative` prop, `HIDDEN_FROM_ASSISTIVE_TECH`'s ~dozen call sites) was actually hidden from a screen reader on web. **Real fix, same family as the two above: add `aria-hidden: true`.** `HIDDEN_FROM_ASSISTIVE_TECH` (`packages/ui/src/a11y/decorative.ts`) now sets it alongside the three legacy flags.
- **`Animated.timing` driving `interpolate(transform)` never advances, and Reanimated's `useAnimatedProps` writing `strokeDashoffset` doesn't reach the DOM either.** Both were measured frozen — the completion callback never fires with `useNativeDriver` true or false; colour changes still work because those are plain re-renders. Measured on the `Toggle` knob (3.2, fixed by computing the transform directly and snapping), the reason §3's Onboarding panel slide was not built (3.12), and the DNA match ring (6.3, `strokeDashoffset` sampled across 1.2s on a live render, sat frozen at its starting value throughout). **10.3 root-caused this: it is one defect, not two, and it is an artifact of the verification harness, not of the app.** Both libraries drive their web timing loop through the same browser primitive, confirmed by reading the installed packages directly, not inferred: RNW's `TimingAnimation.js` (`node_modules/react-native-web/dist/vendor/react-native/Animated/animations/TimingAnimation.js:75,103`) calls `requestAnimationFrame` for every tick of its JS-driven path, and `useNativeDriver: true` never actually engages a native driver on web — `NativeAnimatedHelper.js`'s `shouldUseNativeDriver` (`:404-416`) always falls back to `false` because `TurboModuleRegistry.get` (`TurboModuleRegistry.js:14`) unconditionally returns `null` on RNW, so `true` and `false` are literally the same code path on web, which is exactly why 3.2/3.12/6.3 measured no difference between them. `react-native-reanimated`'s web fallback runtime (`JSReanimated.js:12,22`, `scheduleOnUI`) schedules every worklet tick through `globalThis.requestAnimationFrame` too — same primitive, second library. Chromium fully **suspends** `requestAnimationFrame` callbacks (not merely throttles them) on a hidden document — standard, documented Page Visibility API behavior, not specific to this app — and this repo's verification pane (`Claude_Browser`) reports `document.visibilityState: 'hidden'` at all times, reconfirmed live in 10.3 (a fresh `Animated.timing` transform sampled at rendered `left: 40` twice, 9.6s apart, well past its 3000ms duration, never moved). `setInterval`, the mechanism that does work here, is only clamped on a hidden document, not suspended — the actual, verifiable difference, not a coincidence.
  - **What this means for the three shipped workarounds: none of them was fixing a real product bug, and none needs to be reopened.** In a genuinely foregrounded browser tab, `requestAnimationFrame` runs normally, so `Animated.timing`, Reanimated's `withTiming`/`useAnimatedProps`, and a plain `rAF` loop would all animate correctly for a real user — the freeze is a property of this always-hidden verification pane, not of RNW, Reanimated, or this codebase. The computed-snap `Toggle` (3.2), the deferred Onboarding slide (3.12), and the `setInterval`-driven DNA ring (6.3) are not broken and don't need rewriting to restore "real" animation — a computed snap is simply less good, not incorrect, and rewriting any of the three to use `Animated`/Reanimated again would reintroduce a transform this pane can never verify. If a future task wants real interpolated motion on one of these, that's a product/design call to revisit deliberately, not a bug fix — and it would still need a verification path other than this pane (a real user tab, or a unit-level assertion on the animation driver's internal state rather than the rendered DOM attribute).
  - **Peer-dependency mismatches (async-storage, netinfo, react-native-svg — Metro warns on all three at boot) were considered and ruled out**, not left unexamined: the `setInterval` rewrite proves `strokeDashoffset` writes through the installed `react-native-svg` version work fine when written by a plain re-render; what's frozen is the _tick source_ feeding the write (`requestAnimationFrame`), not the SVG attribute path itself, and that tick source is shared by both `Animated` and Reanimated regardless of package version.
  - **Verification limit, stated plainly rather than glossed over:** this task could not get a second, independent read from a genuinely visible tab — the Claude-in-Chrome extension was not connected this session, and `computer-use`'s browser grant is restricted to screenshot-only (no navigation) specifically to prevent working around that boundary. The conclusion above rests on direct inspection of the installed animation libraries' source plus the Page Visibility API's well-documented, standard behavior, not on a second empirical sample outside this pane. That is a materially stronger basis than the "no root cause found" state this entry replaces, but a future session with real-browser access could still close the loop with one more visible-tab sample if it's ever in doubt.
- **`Icon name="..."` resolved to `undefined` on web** until 3.3 replaced the dynamic `require` with a static map. Fixed — listed so the symptom (a neutral placeholder box where a glyph should be) is recognisable if it returns.

The a11y entries are input to **8.2**, the accessibility pass; the `Animated` entry and the two below it are input to **6.3**, the only task in the list that animates anything.

**Standing rule, decided by 8.2, superseding the "fold the value into the label" workaround the first two a11y entries above used to prescribe: use the `aria-*` prop, not a label rewrite.** All three a11y traps above look identical — a legacy accessibility prop that RNW's `createDOMProps` (`node_modules/react-native-web/dist/modules/createDOMProps/index.js`) simply never reads — but a real, non-workaround fix exists for all three, found by reading `createDOMProps` against React Native's own `View.js` (`node_modules/react-native/Libraries/Components/View/View.js:64-113`). `createDOMProps` _does_ read the modern `aria-*` prop names (`aria-valuenow`, `aria-selected`, `aria-checked`, `aria-hidden`, …) and copies them straight to the DOM; `View.js` reads those same `aria-*` props and merges them back into `accessibilityValue`/`accessibilityState`/`accessibilityElementsHidden`/`importantForAccessibility` for the native renderer. So `aria-*` is RN 0.71+'s own cross-platform spelling of the legacy props, not a web-only prop — adding it is not the fork this doc forbids, it is keeping the correct cross-platform prop _in addition to_ the legacy one, exactly as the rule above already asks. **Do not reach for "put it in the label" on a new instance of this trap — add the matching `aria-*` prop instead**, and keep the legacy prop too (costs nothing on native, guards against an RN version where the bridge above is ever missing). Every `<ProgressBar accessibilityLabel>` call site in the app (`@gmrlog/ui`'s `DistributionBars`, the DNA match bars, achievement/contribution/level progress) was checked as part of 8.2's audit that this value-in-the-label pattern was already followed everywhere except one straggler (`profile-hero.tsx`'s level `ProgressBar`, labelled `"Level N progress"` with no number) — now fixed, and now redundant with `ProgressBar`'s own `aria-valuenow`, but not wrong to keep since a caller-supplied label can carry more than the bare number. **The `accessibilityState` sweep this paragraph used to defer is done — re-audited 2026-08-23 and every one of the app's 32 `accessibilityState` call sites already reaches the DOM.** 8.2 flagged "roughly twenty" consumers (`theme-selector.tsx`, `profile-tabs.tsx`, `spoiler-badge.tsx`, `star-rating.tsx`, and others) carrying neither the state in a label nor the `aria-*` prop; all four named files, and the other twenty-eight sites, now carry it. Three shapes cover them, and the last two are why a grep for `aria-selected` alone under-reports the real coverage: the site adds the prop itself; or it sets state through a `@gmrlog/ui` primitive that derives both spellings internally from its own prop (`Chip`, `Button`, `IconButton`, `Toggle`, `SegmentedTabs`); or the state is `disabled`, which needs nothing added — RNW's `Pressable` writes `aria-disabled` from its own `disabled` prop (`node_modules/react-native-web/dist/exports/Pressable/index.js:125`) and `TextInput` maps `editable={false}` to `readonly` instead (`exports/TextInput/index.js:368`), which is the more accurate semantic for a field that is still focusable. **What is genuinely dead on web is the `accessibilityState` object itself** — it appears nowhere in `createDOMProps`' prop list, so none of its keys, `disabled` included, is forwarded by that route; keep it anyway, native reads it. Two call sites were passing a redundant `accessibilityState={{ selected }}` on top of a `Chip` that already derives it, which silently dropped `Chip`'s own `disabled` from the state via the `{...rest}` spread; both removed.

## Known environment traps

The local stack fails quietly in ways that look like application bugs. Check these before debugging code.

- **Redis dies on its own, and the backend does not recover.** Fourth silent drop in four sessions (3.13, 3b.1, 3b.1a, 3b.2b). **It can also die mid-session:** on 3b.2b it answered `PONG` at the opening check and had stopped by the time the backend booted forty minutes later, so the boot log carried `platform redis connect deferred` and the first write answered 503. Re-check it after any long build, not only at the start. The container simply stops; the backend's ioredis client deferred its connect at boot and never retries, so every rate-limited route answers `503 INTEGRATION_UNAVAILABLE` (`RATE_LIMIT_REDIS_UNAVAILABLE`, "redis not ready") — which reads as an auth bug until you look at the log. **Restarting the container is not enough: restart the backend after it.** Check `docker exec gmrlog-redis redis-cli ping` before blaming sign-in.
- **A native Windows PostgreSQL service listens on 5432 and shadows the container. Use 5433 — which is what the repo's own `.env` already says.** This is the most expensive trap in this list because nothing about it looks like a connection problem: the host connects fine, authenticates fine as `gmrlog`, and finds a database called `gmrlog`. It is simply **the wrong one** — 151 tables against the container's 87, `users.id` typed `uuid` rather than `text`, and no `user_consents` or `account_deletion_requests` at all. Prisma then fails in ways that read as a corrupt client: `P2022` naming a column that does not exist, `P2021` naming a table that does, and `P2023 "Error creating UUID … found \`x\`"`on a`cuid()`primary key. **The reported column name was the Turkish word`sütunu`** — the native install runs a Turkish locale, Postgres emitted a localized error, and Prisma's message parser extracted the wrong token; the metadata is garbage, so do not chase the name it gives you. Two things make this hard to see: `docker exec gmrlog-postgres psql …`runs *inside* the container, so every hand-check passes and the container's log shows no error for the query that just failed; and`docker compose … up -d postgres`from the repo root does **not** read the root`.env`(compose looks beside the compose file, in`docker/`), so the container publishes 5432 by default and appears, in `docker ps`, to be the thing on that port. It is not — the native service wins. **Diagnose it in one call, from the host, not from inside the container:** `select current_setting('data_directory')`answers`/var/lib/postgresql/data`for the container and a Windows path for the native service. Bring the container up with`POSTGRES_PORT=5433 docker compose -f docker/docker-compose.yml up -d --force-recreate postgres`and point`DATABASE_URL` at 5433. Do not stop the user's native service.
- **The backend loads `@gmrlog/database` from `dist`, and its watcher does not cover `packages/`.** Editing a repository under `packages/database/src` changes nothing at runtime until `pnpm --filter @gmrlog/database run build` **and** a backend restart. Worse, that build runs `prisma generate`, which fails with `EPERM … query_engine-windows.dll.node` while a backend is running — so the order is: stop the backend → build → start it. A source edit that silently does nothing is indistinguishable from a wrong fix.
- **Metro is started with `CI=1`,** which disables the watcher along with the interactive menu. Every frontend edit needs a Metro restart, and it must not start before `@gmrlog/ui` finishes building.
  - **Metro is not slow, and "Metro wedged" should not be the first explanation.** Measured across two consecutive sessions: first bundle **16.0s**, then **2.5s / 2.3s** on restart, with in-session rebuilds under **700ms**; a `--clear` restart binds in about a minute. 3b.2 recorded it as wedging and then as "ten minutes plus"; neither reproduced in four Metro starts since. Budget a normal minute, and if it really does stop, say what it printed rather than assuming the documented failure. What _is_ real is the `CI=1` restart requirement above — an edit that seems not to apply is almost always that.
  - **`preview_start` can bind Metro and then silently kill it.** `preview_start({name: 'frontend-web-ci'})` reported success and bound port 8081, then the process disappeared within a minute — no entry in `preview_list`, nothing left on the port, no error surfaced anywhere. This is the most expensive class of failure here precisely because it looks like success. The working fix is a plain backgrounded shell command instead: `CI=1 pnpm exec expo start --web --clear --port 8081` from `apps/frontend`, which binds and holds. If `preview_start` claims success but the pane won't load anything, don't retry `preview_start` — go straight to the manual command.
- **The release-gate script leaves data behind.** `scripts/release/smoke-d3-24-release-gate.mjs` creates a `Gate Community <timestamp>` on every run and never removes it; the local database holds ~100k of them. They have no owner membership row, so they are invisible to the app but they are real rows in every unpaginated query.
- **Signing in (no longer a blocker).** Several earlier sessions recorded live verification as blocked on sign-in. It isn't: `scripts/release/lib/common.mjs` (`registerUser`/`login`) exercises the real auth surface with throwaway `<handle>@smoke.gmrlog.local` fixture accounts, password `SmokeTestPass12`, hitting `POST /api/v1/sessions/register` (which itself returns tokens) or `POST /api/v1/sessions` — no manual account creation, no credentials typed. Verified live 2026-08-15: a fresh `register` call against a running backend returns 201 with `accessToken`/`refreshToken` in the body. **The trap:** the web build's `SecureStorage` adapter (`apps/frontend/lib/storage/expo-secure-storage.ts`) prefixes every key with `gmrlog.secure.` before writing to `localStorage`, and `session-manager.ts` names its keys `gmrlog.session.access`/`gmrlog.session.refresh` — so the actual `localStorage` keys are `gmrlog.secure.gmrlog.session.access` / `gmrlog.secure.gmrlog.session.refresh`, not the bare `gmrlog.session.*` names. Reading the bare names (or writing them by hand to fake a session) looks exactly like an expired/missing session. Use the double-prefixed keys for any DOM-level session read or write in the Browser pane.
- **The Browser pane reports `document.visibilityState: 'hidden'`, and this has now broken a functional path, not only `screenshot`.** First seen as `screenshot` timing out — read as a compositing/capture limitation, nothing more. Second time, closing 3b.1c/3b.1f, it gated TanStack Query's retryer: `focusManager.isFocused()` reads the same `visibilityState`, so a query's one scheduled retry paused forever after its delay with no error rendered and no Retry button, on a screen that looked correctly wired end to end. Third time, 6.3's DNA match ring: Chromium fully **suspends** `requestAnimationFrame` callbacks on a hidden document — not merely throttles them, the callback queue just stops — so a plain `rAF`-driven tween sampled dead-frozen in this pane despite being ordinary React state updates with no animation library involved. `setInterval` was the fix, because Chromium only clamps a hidden tab's timer rate (to ~1/s) rather than suspending it outright, so it is provably testable in this pane and behaves identically for a real, visible user's tab. Treat `visibilityState: 'hidden'` as a standing fact of this environment that can gate real application logic — retry timers, **and now animation timers** — not a screenshot-only quirk: before trusting a measurement that involves a delay, a retry, a resume, or an animation, check whether anything in the path depends on tab focus or visibility, and reach for `setInterval` over `rAF` if the mechanism itself needs to be verified from here.

## Working rhythm

`TASKS.md` holds the ordered checklist. At the start of a session, read it, take the next unchecked task, and do only that task. When it is done and committed, tick the box and stop.

Do not skip ahead, do not batch several tasks into one diff, and do not start a task whose dependency is still unchecked.

If a task turns out to be wrong or already done, say so and tick it with a note rather than inventing work.

A branch counts as "measured" only when the write-up names the state, the screen, and the fault it was seen under — "verified end to end" alone is not a closure (3b.1c closed on a real but non-generalizing pass; reopened when 3b.1f hit the same acceptance test and it failed).

## Settled decisions

Calls already made and closed. Do not re-litigate them inside a screen or feature task; if one needs to be reversed, reverse it by fixing what made it necessary, not by quietly reintroducing the old behavior.

- **Automatic query retry is off** (`retry: false` on `createAppQueryClient()`'s defaults, `query-client.ts`). 3b.1c's first fix taught the failure paths not to wipe the session and not to latch offline; that closed the acceptance test once, but 3b.1f hit the identical test and it still failed, because a fourth, deeper mechanism was gating it — TanStack Query's retryer resumes a _scheduled_ retry only when `focusManager.isFocused()` is true, which reads `document.visibilityState !== 'hidden'`, and this pane reports `'hidden'`. With a retry configured, a failed query can pause forever after its delay with no error and no Retry button, stranding a real user who backgrounds the tab at the wrong instant — worse than failing fast. Every list/detail screen already ships its own explicit, user-triggered Retry, so the automatic one was UX sugar sitting in front of a silent trap, not load-bearing behavior. **It will not be silently re-added.** If it comes back, it comes back by resolving the focus gate itself (teaching the retryer or the environment not to depend on tab visibility), not by flipping the flag and re-measuring once.
  - This is also the concrete case **3b.2b** exists to prevent, and it happened anyway: 3b.1c changed a global default (`query-client.ts`) from inside a screen-branch task. The rationale — "every list/detail screen already has its own Retry" — is true for every screen written to date, but as a global default it also covers every mutation and every screen not yet written, none of which were audited when the flag flipped. Recorded here so the next task that touches retry behavior sees it as a standing global decision, not a note buried in one screen's closing paragraph.

- **`UserConsent` is append-only, and `(user, document, version)` is no longer unique.** It was, which made a second decision on the same version an UPDATE in place: an accept → withdraw → accept sequence left one row saying `accepted` and no trace of the window during which consent was not held — the evidence a controller has to be able to produce, and the opposite of what the repository's own docstring and `LegalConsentStateResponse.decisions` ("History, not just the current state") both promised. The current answer for a version is the **newest row** for it. Ordering is by the `sequence` column, never `decidedAt`: `decidedAt` is millisecond-precision and a batch write ties on it, and a tie in an evidence table is the whole problem. Nothing may reintroduce a unique key on those three columns, and nothing may resolve "current decision" from a timestamp.
- **`DatabaseClient` is `PrismaClient | Prisma.TransactionClient`,** which is what its own doc comment always claimed ("a live `PrismaClient` or a transaction-scoped client both satisfy this") and the type used to refuse. A repository that wants to group its own writes calls `withTransaction(this.db, fn)` rather than `this.db.$transaction` — Prisma has no nested transaction, so when the caller already opened one, `withTransaction` runs inline inside theirs. `SessionsService.register` is the case that forced it: four writes across three repositories under a comment claiming atomicity it did not have.

## What not to do

- Do not copy anything out of `GMRLOG.dc.html`. It is HTML with inline styles; every value in it has a token equivalent. Read it to understand intent, then write React Native.
- Do not add a colour, font family, spacing value or radius that is not in the theme.
- Do not create a new screen when a doc says extend an existing one.
- Do not use emoji in the product UI.
- Do not add analytics, tooltips, onboarding hints or empty-state illustrations that were not asked for.
