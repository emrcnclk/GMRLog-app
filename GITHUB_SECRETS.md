# GitHub Actions secrets — GMRLog production deploy

Governs [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml), which fires on
`git push --tags v*` (or manual `workflow_dispatch`) and deploys to the `production`
GitHub Environment.

**Read this before adding anything:** this repo's deploy pipeline deliberately keeps
application secrets (JWT_SECRET, SMTP creds, STEAM_WEB_API_KEY, SENTRY_DSN, ...) _out_
of GitHub entirely. They live only in `infrastructure/deploy/.env.deploy.local` on the
production host, generated by [`scripts/deploy/gen-secrets.mjs`](scripts/deploy/gen-secrets.mjs)
and gated by [`scripts/deploy/preflight-deploy-env.mjs`](scripts/deploy/preflight-deploy-env.mjs).
CI never sees them, never templates them, and never has a reason to. If a future change
wants CI to inject one of those into the env file directly, that's a deliberate
architecture change, not a missing secret — don't add it here without also removing it
from the host's manual setup.

What GitHub _does_ need is narrower: enough to SSH into the host, know where the deploy
directory is, and push a built image tag. That's five secrets and one variable.

## Where to add them

Repo → **Settings → Environments → `production`** (not repo-level _Secrets and
variables_, unless you want them readable by every workflow). `deploy.yml` references
the `production` environment explicitly:

```yaml
environment:
  name: production
  url: https://${{ vars.API_DOMAIN }}
```

If the `production` environment doesn't exist yet, create it here first — optionally
with a required reviewer, which pauses every tagged deploy for a human approval before
it touches the host.

## Required secrets

| Secret                   | Used for                                                                                                                                                                                     | Example value                                                                  | How to generate                                                                                                                         |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------- |
| `DEPLOY_SSH_KEY`         | Private key the runner uses to SSH into the host and run `deploy.sh`                                                                                                                         | `-----BEGIN OPENSSH PRIVATE KEY-----\n...` (full PEM, including header/footer) | `ssh-keygen -t ed25519 -f deploy_key -C "gmrlog-deploy" -N ""` then paste `deploy_key` (not `deploy_key.pub`)                           |
| `DEPLOY_SSH_KNOWN_HOSTS` | Pins the host's SSH fingerprint so the runner doesn't blindly trust whatever answers on first connect (see the comment in `deploy.yml` — this is the actual MITM mitigation, not decoration) | `api.gmrlog.com ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAI...`                      | `ssh-keyscan -H api.gmrlog.com` (run this _from a trusted network_, or better, copy the fingerprint the host prints on first provision) |
| `DEPLOY_HOST`            | Hostname/IP the runner SSHes to                                                                                                                                                              | `api.gmrlog.com` or `203.0.113.42`                                             | n/a — your host                                                                                                                         |
| `DEPLOY_USER`            | SSH user on the host (needs Docker + rsync target write access, does **not** need root if that user is in the `docker` group)                                                                | `deploy`                                                                       | n/a — your host                                                                                                                         |
| `DEPLOY_PATH`            | Absolute path on the host that `infrastructure/deploy/` gets rsynced into                                                                                                                    | `/opt/gmrlog/deploy`                                                           | n/a — your host                                                                                                                         |

## Required repository/environment variable (not a secret)

| Variable     | Used for                                                                                                                  | Example value    |
| ------------ | ------------------------------------------------------------------------------------------------------------------------- | ---------------- |
| `API_DOMAIN` | Builds the environment URL shown in the deploy summary, and is the hostname the final smoke-test step curls over real TLS | `api.gmrlog.com` |

Set under the same **Environments → production → Variables** tab, not Secrets — it's
not sensitive and appears in the deploy log regardless.

## What is _not_ a GitHub secret, and why

| Not here                                                                                   | Actually lives                              | Why                                                                                                                                                                                                                                                                                                                  |
| ------------------------------------------------------------------------------------------ | ------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GHCR_TOKEN`                                                                               | N/A — uses `secrets.GITHUB_TOKEN`           | The `image` job authenticates to GHCR with the workflow's own automatic token (`docker/login-action` + `secrets.GITHUB_TOKEN`), scoped to `packages: write` in the job's `permissions:` block. Adding a personal `GHCR_TOKEN` would be a second, wider-scoped credential doing a job the automatic one already does. |
| `JWT_SECRET`, `POSTGRES_PASSWORD`, `MEILI_API_KEY`, `MINIO_ROOT_PASSWORD`, `METRICS_TOKEN` | `.env.deploy.local` on the host, gitignored | Generated on the host by `gen-secrets.mjs`, never transmitted to or from CI. A GitHub secret would mean the value round-trips through Actions' logs/environment on every run for no benefit.                                                                                                                         |
| `STEAM_WEB_API_KEY`, `SMTP_*`, `SENTRY_DSN`, `GOOGLE_*`, `DISCORD_*`, `IGDB_*`             | Same file, filled by hand                   | Third-party credentials that can't be generated; still host-only, same reasoning.                                                                                                                                                                                                                                    |
| `SENTRY_AUTH_TOKEN` (release/sourcemap upload)                                             | Not currently wired into CI at all          | Add only if you extend `deploy.yml` to call `sentry-cli releases new`. Out of scope for the pipeline as it exists today — don't add this secret speculatively.                                                                                                                                                       |

## Verifying nothing is a placeholder

The five secrets above are opaque strings GitHub itself doesn't validate. What _does_
validate is `preflight-deploy-env.mjs`, run automatically as the first step of the
`Release` job on the host — it fails the deploy outright if `.env.deploy.local` still
contains `CHANGE_ME` or a handful of known-weak defaults (`gmrlog`, `minioadmin`,
`password`, ...). See [`DEPLOY_SECRETS_GENERATOR.sh`](DEPLOY_SECRETS_GENERATOR.sh) for a
one-shot way to generate the SSH key and stage the host secrets together, and
[`VERIFICATION_CHECKLIST.md`](VERIFICATION_CHECKLIST.md) for the pre-deploy checklist
that ties this back to the other six documents.

## Quick reference — generation commands

```bash
# DEPLOY_SSH_KEY / its .pub counterpart (add .pub to the host's authorized_keys)
ssh-keygen -t ed25519 -f ./gmrlog_deploy_key -C "gmrlog-deploy" -N ""

# DEPLOY_SSH_KNOWN_HOSTS (run once the host is reachable; verify the fingerprint
# out-of-band — e.g. against what your cloud provider's console shows — before
# trusting it)
ssh-keyscan -H api.gmrlog.com

# Host-side application secrets (NOT GitHub secrets — see table above)
node scripts/deploy/gen-secrets.mjs --domain api.gmrlog.com --email ops@gmrlog.com
```
